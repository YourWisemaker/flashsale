# Plan: virtual waiting room (open decision)

**Status:** Open. Recommendation: don't build it now.
**Owner:** Arief Fitranto

## Question

Should visitors queue in a waiting room before they can reach `POST /api/purchase`?

## What a waiting room is for

It protects a backend that can't take the spike (a slow checkout, a payment provider, a database doing the stock decrement) by admitting visitors at a fixed rate.

## Where this system stands (ADR 0011, PERFORMANCE_REVIEW.md)

- The purchase decision is one Redis Lua script, about 1ms, no database on the path.
- Measured 16,000 to 19,000 req/s through the full stack from one client; 52,700 req/s raw with 2 API processes.
- Per-account rate limit (5/s), load shedding past 200ms event loop lag, and the BullMQ queue already pace everything slow (the Mongo write).
- There is no payment step, so nothing downstream needs protecting.

## Options

| Option | How | Cost | Gain |
|---|---|---|---|
| A. Nothing (current) | Rate limits + shedding + queue | none | Already holds at measured load |
| B. Redis ticket queue | `SET NX` ticket per user, `INCR` position, admit cursor from Redis time `(now - startsAt) * rate + burst`; a small Lua check before the gate | new keys, a new 403/425-style status, UI for "you're in line", tests | Fairness by arrival order instead of by reflexes |
| C. Edge waiting room | CDN or gateway product (e.g. a managed queue page) | vendor config, outside the repo | Absorbs bot floods before they reach the API |

## Recommendation

A. Revisit B if a payment step or any slow downstream is added, or if fairness by arrival order becomes a product requirement. Revisit C for a real launch with bot traffic.

## If B gets picked

- [ ] ADR 0012 or next: waiting room semantics and the admit formula
- [ ] Core: `waiting-room.lua` and keys in `keys.ts`; property tests against a reference model
- [ ] API: check before the gate (never inside `purchase.lua`), new status in `openapi.yaml`, README, `apps/web/src/api.ts`
- [ ] Web: "you're in line" state in `BuyBox`, `messages.ts`
- [ ] Defaults keep stress and e2e passing unchanged
- [ ] Stress scenario for admission rate; mutation 100%
